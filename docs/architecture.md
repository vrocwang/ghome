# 一次 push 是怎么走到浏览器的

[README](../README.md) 只留下"push 后 1~2 秒生效"这一句；这里是把整条链路、以及为什么
这么设计写清楚。

## 服务器侧

```text
   你 git push
        │
        ▼
   Gitea ──webhook(HMAC 签名)──▶ POST /api/webhook
        │                              │  校验签名 + 只认 push 事件
        │                              ▼
        │                        防抖 1.2s（一次 push 可能触发多个钩子）
        │                              │
        │                              ▼
        │                        GET /api/v1/repos/.../contents/nav.yaml
        │                        GET /api/v1/repos/.../contents/custom.css
        │                              │  都带上 token，只有服务端看得到
        │                              ▼
        │                        解析 + 校验整份 YAML
        │                          ├─ 通过 → 换上新配置，广播 SSE
        │                          └─ 不通过 → 保持旧配置，/healthz 标 degraded
        │                       两份文件的修订号合成 themeRevision
        │                              │
        ▼                              ▼
   60s 轮询兜底 ──▶ 重新读上面两个文件   GET /api/events  (浏览器长连接)
   （服务器侧）                          │  事件只有一种："变了，重新读"
                                         ▼
                          重新拉 /api/nav + /api/status + theme.css
                                         │
                                         ▼
                            版本号变了才重绘 + "导航已更新" 提示
                          浏览器侧另有 60s 兜底：SSE 建不起来时直接轮询 /api/nav
```

事件类型只有一种（"变了"），浏览器收到后重新拉取并按版本号决定要不要重绘。这样即使通知被
合并或丢弃，也不会出现"配置更新了但状态灯没更新"这种半新半旧的状态。

**为什么 webhook 之外还留服务器侧轮询？** webhook 是尽力而为的：forge 重启、网络抖动、
密钥改错、钩子被误删，任何一种都会让更新静默停掉，而静默停掉是最难发现的故障。轮询是那份
保险，代价是每个 `--poll` 间隔多一次 API 请求（`--poll=2s` 实测 8 秒内 4 次，`--poll=0` 是
1 次，仅启动）。

## 浏览器侧

浏览器侧也有两条独立的路：

| | 方向 | 何时用 |
| --- | --- | --- |
| **SSE** `/api/events` | ghome → 浏览器，服务器主动推 | 主路径。页面一加载就连，配置一变就收到 `changed`，实测 1.8 秒内更新完毕 |
| **兜底轮询** `/api/nav`，每 60 秒 | 浏览器 → ghome，浏览器主动问 | SSE 建不起来时。SSE 一旦 `open` 就停掉，所以正常情况下它一次都不发 |

**是自动更新，不是自动刷新**——整个前端没有一处 `location.reload()`：配置变化只原地重渲染，
滚动位置也保留。样式表是单独跟踪的：`/api/nav` 的 `meta` 里有两个修订号，`revision` 管要不要
重绘整个页面，`themeRevision` 覆盖 `nav.yaml` 和 `custom.css` 两份文件、管要不要重新拉
`/theme.css`（它同时是 cache buster）。所以只改 `custom.css` 的推送也能生效，即使 `nav.yaml`
的 blob SHA 没动。两者由服务端在同一个原子操作里发布，不存在"样式更新了但配置还是旧的"
这种中间态；`/healthz` 里两个值都能看到。

**别把两个 poll 弄混。** `GHOME_POLL` 管的是「ghome 多久去问一次 forge」；浏览器的 60 秒
兜底问的是 ghome。关掉 `GHOME_POLL` 不影响浏览器：SSE 照旧、兜底轮询照旧，只是如果没人推
新配置，浏览器每次拿到的还是同一份。

文件模式有个额外前提：**ghome 不用文件系统通知**，所以"改文件页面就变"依赖的仍是轮询或
webhook。`--poll=0` 配文件模式，等于只在启动时读一次。

## 为什么坏配置不覆盖好配置

导航页是入口，挂掉影响所有人。所以结构性问题（YAML 语法错、缺 `url`、危险协议、整份配置
一个链接都没有）会让整份文档被拒：页面继续显示上一版好配置，`/healthz` 变成 `degraded` 并
给出 `lastError`，改好再 push 自动恢复，回滚只需要 `git revert`——都不需要重启。

表面问题（字段名拼错、颜色词写不对、非法热键）只忽略那一项，其余照常更新，并在页面顶部和
日志里给提示；这一层的期望是"容忍但不隐瞒"。

## 进程内状态

配置换新时，所有派生状态都从一个地方重算（`main.go` 的 `applyConfig`），所以图标允许列表、
预热目标、探测目标和正在服务的配置不可能各说各话：

| 派生状态 | 来源 | 何时重建 |
| --- | --- | --- |
| 图标允许列表 + 预热 | 公开条目的 `IconURLs()`（每 host 一个 URL） | 每次配置更新 |
| 探测目标 | 全部条目的可探测 URL | 每次配置更新 |
| 探测器实例 | `status.interval/timeout/concurrency` | 只有这三个值变了才重建，避免改个标题就丢掉已有探测结果 |
| 缓存文件 | 当前配置 + 仓库里的 `custom.css` | 每次成功更新 |
