# 图标的解析与安全边界

[README](../README.md) 的「图标是怎么来的」只留结论。这里是被移出来的细节。

## 联网那一层：只猜 `<host>/favicon.ico`

服务端**不抓页面、不解析 HTML**。一个 host 一次请求，拿 `<host>/favicon.ico`，然后校验它确实是图片：

1. 请求 `http(s)://<host>/favicon.ico`，UA 是 `ghome-icons/...`。
2. 校验返回的确实是图片：先看 `Content-Type`（认不出时用前 512 字节嗅探）。不是图片就算失败。
3. **失败不重试**：这一次拿不到就记下来，这个 host 在本进程生命周期内不会被再问一次。
   "这个站点没有 `/favicon.ico`"是关于站点的事实，不是关于此刻的事实，每次开页面都重问一遍正是
   导航页最不该产生的流量。重启进程（或改 `FailureTTL`）才会重新尝试。

这么做的代价很具体，值得记住：**图标路径是哈希的站点拿不到图标**，例如
`https://x.example/` 把图标放在 `/assets/favicon-a1b2c3.svg`，而根路径没有 `favicon.ico`。
这类站点会显示字母头像。想给它真图标，用 `--icon-dir` 放一个 `<host>.svg`，或在链接上写自己的
`icon:`——两条路都不联网。

为什么不做"读页面找 `<link rel="icon">`"：那是每个 host **两次**请求（页面 + 图标），而且每次都要下载
一份 HTML。对一份有几百个链接的导航页来说，那是几百份文档的流量，换来的只是少数哈希图标的覆盖率。
这条路被有意删掉了（`git log` 里能查到），要恢复它意味着把页面抓取和 HTML 解析重新加回来。

### 各种链接分别怎么处理

| 链接写法 | 图标怎么办 | 状态灯 |
| --- | --- | --- |
| `https://site.example/` | 抓 `https://site.example/favicon.ico` | 探测 |
| `https://site.example/deep/page?q=1#frag` | 同上：只用 origin，**path/query/锚点一概不用**（favicon 按标准就在站点根上，浏览器地址栏也是这个行为） | 探测 |
| `http://192.168.1.10:8080/app` | 抓 `http://192.168.1.10:8080/favicon.ico`。IP 就是 hostname，端口保留；**纯 http、不涉证书** | 探测 |
| `http://nas:9090/`（同 host 已有 `:8080`） | 复用 `:8080` 那张：缓存键和 `h=` 参数都**剥端口**，一个 host 只有一张图标。要区分就给链接写 `icon:` | 探测 |
| `https://self-signed.internal/` | **握手失败 → 字母头像**：只信系统 CA，没有 `--insecure-tls` 这类开关。要图标就放 `--icon-dir` 或写 `icon:` | 探测（同样因证书失败 → 状态灯报错） |
| `ws://host/socket`、`ssh://`、`vscode://`、`mailto:` | 不抓（也抓不到）。前端生成字母头像 | 不探测 |

非 http(s) 的链接**不进允许列表**：允许列表只收 `http`/`https` 的 host，所以服务端不会被指使去连一个
`ws://` 或 `ssh://` 地址；它们对图标和状态灯都是纯粹的展示条目。

## 查找顺序

一次 `/api/icon?h=<host>` 请求，按下面的顺序找，命中就停：

| 顺序 | 拦在哪 | 说明 |
| --- | --- | --- |
| 1 | `--icon-dir` 本地文件 | 命中就**完全不联网**，也不查缓存（实测 0.4 ms） |
| 2 | 服务端内存缓存 | 见下表 |
| 3 | 联网猜 `<host>/favicon.ico` | 见上一节；`--icon-fetch=off` 时这一步直接跳过 |
| 4 | 浏览器缓存 | 7 天（`Cache-Control: private`，因为答案与调用方有关），URL 带 `?v=<配置 revision>`，配置一变就自动失效 |

## 本地图标目录（`--icon-dir`）

内网服务大多没有 favicon，DNS 也可能根本解析不了，而本地文件不需要网络也不需要 DNS——
所以这是内网部署的可靠解。

```bash
ghome --icon-dir=/var/lib/ghome/icons
```

```text
/var/lib/ghome/icons/
├── git.internal.svg      # 给 https://git.internal/
├── nas.png               # 给 http://nas:8080/ 和 http://nas:9090/
└── grafana.internal.svg
```

- 文件名是 `<host>` 加扩展名，按 `.svg` → `.png` → `.ico` → `.webp` → `.jpg` → `.jpeg`
  取第一个存在的。
- host **转小写并剥掉端口**，所以 `nas:8080` 和 `nas:9090` 都找 `nas.svg`。
- 超过 512KB 的文件会被忽略。
- 目录不可用只打一条 WARNING，不会拒绝启动：图标只影响好不好看，为一个拼错的路径把整个
  导航页拒绝掉是本末倒置。但也不会静默——启动日志会报可用图标数量。

**一个 host 只有一个图标。** `/api/icon` 按 host 查，服务端取配置里**第一个**用它的链接来
解析。想同机的不同服务各有图标，用链接自己的 `icon:` 字段，或在 `--icon-dir` 里放对应的文件。

## 关掉联网抓取（`--icon-fetch=off`）

```bash
ghome --icon-fetch=off --icon-dir=/var/lib/ghome/icons
```

- **服务端不再发起任何图标相关的出站请求**：启动和每次配置重载的预热跳过（`Warm` 直接返回），
  `/api/icon` 对没有本地文件的 host 一律 404。
- 前端拿到 404 后走已有的 `onerror` 回退，渲染**由链接名生成的首字母头像**（color 由名字哈希决定），
  所以视觉上和"这个站抓不到图标"完全一致。
- `--icon-dir` **不受影响**，仍然是第一优先级：它本来就不联网，关掉抓取正好让它成为唯一的图标来源。
  反过来，配了 `--icon-dir` 的 host 现在**连预热也不会去抓**（否则"用本地图标省流量"会被预热抵消）。
- **命中和 404 都带 7 天缓存**（`private, max-age=604800`），URL 由前端加上 `?v=<revision>`：
  在同一个 revision 内，一个 host 的图标或"没有图标"只会被问一次。缓存键是 URL 而不是结果，所以
  改了 `--icon-dir` 或往目录里补了图标，要等 revision 变（或者硬刷新）才会看到——和 7 天前的旧
  图标压着不清是同一件事。
- 显式写在链接上的 `icon:` 是浏览器直连，不受这个开关影响：它不下发任何服务端请求。真要端到端零请求，
  就用 `data:image/...` 或 emoji（见下一节）。
- 取值只有 `auto`（默认）和 `off`（`none` 是同一个意思），其它值**启动即报错**，不会静默按
  `auto` 处理。
- 浏览器侧可能还压着 7 天前抓到的图标：`?v=` 只随配置 revision 变，改这个开关不会让 revision 变，
  所以想立刻看到生成的头像要硬刷新一次。服务端的抓取是**当场**停的。

**两个 key 容易混**：本地图标目录按剥掉端口的主机名找，内存缓存按完整的页面 URL 记。但因为
按 host 预热，一个 host 只会有一次抓取、一个缓存条目，所以两者在实际使用中是一致的。
唯一要注意的是：**内存缓存不持久**，每次重启都会重新预热一遍（实测：3 个链接全在同一 host
时启动预热 1 次上游请求——按 host 去重——之后连打 5 次 `/api/icon` 上游 0 次、每次约 2.5 ms）。

## 缓存

| | 值 |
| --- | --- |
| 条目上限 | 512 |
| 字节上限 | 8 MB（总共） |
| 单个体积上限 | 512 KB |
| 成功结果 | 24 小时 |
| 失败结果 | **本进程生命周期内不再重试** |
| 存续 | 仅内存——重启后重新预热 |

两个上限都要满足。只限条数的话，512 × 512KB 最坏是 256 MB，而这是个空载十几 MB 的服务。

**缓存键是完整的页面 URL**，不是 host。但 `/api/icon` 是按 host 查的，而 `Config.IconURLs()`
把每个 host 归约成一个 URL（配置里第一个用它的链接），预热和端点都从这一份取值——所以
一个 host 实际只会有一个键被用到。

早先的版本按 `PageURLs()` 预热，同一个 host 上的每个链接都会被各抓一遍页面和图标。那些
结果永远不可能被服务到（一个 host 只有一个图标），纯属浪费；现在按 host 归约。

## `/api/icon` 的安全边界

- **只服务当前配置里出现过的 host**，不是开放代理。别人拿不到 `h=` 任意值去驱使服务端抓取。
- 响应带 `Content-Security-Policy: default-src 'none'; sandbox`。第三方 SVG 是从我们自己的
  domain 发出去的，不加这个，直接打开图标 URL 就能执行脚本。
- **允许列表管的是每一跳**，不只是第一个 URL：`<host>/favicon.ico` 若 302 跳到别的 host，
  这一跳会被拒绝（跳转链也有次数上限）。
  代价是**图标被重定向到 CDN 的站点抓不到**——这种情况用 `--icon-dir` 放一个本地文件。
- 浏览器侧：favicon 走这个代理，所以那条路径上不访问第三方。但配置里显式写的
  `icon:` / `logo:` 图片 URL 是浏览器直连的，所以 CSP 的 `img-src` 是
  `'self' data: http: https:`（`http:` 是给纯 HTTP 的内网部署留的）。
- 响应带 `Cache-Control: private, max-age=604800`，**没有 ETag / Last-Modified**，所以浏览器
  在 7 天内不会重新验证。换了 `--icon-dir` 里的文件需要硬刷新（配置 revision 变化会让 URL
  里的 `?v=` 变，也能自动失效）。`private` 而不是 `public`，是因为答案与调用方有关（只被私密
  条目使用的主机对任何调用者都是 404），共享缓存不该把它转给别的调用者。
